# NetGuard Threat Model (Section 21)

Every row below was checked against the actual code/config in this repo as of
this audit pass, not assumed from the spec. "Existing mitigation" cites the
file/mechanism directly. "Residual risk" is stated plainly rather than
claiming anything is fully closed — see Section 22 of the spec.

| ID | Threat | Attack path | Existing mitigation | New/remaining mitigation | Residual risk | Detection | Recovery |
|---|---|---|---|---|---|---|---|
| T1 | API RCE | Vulnerable dependency, deserialization bug, or injection in `api` container | Network isolation (api has no route to `netguard-execution`/devices or `netguard-secrets`/OpenBao — see docker-compose.yaml networks); `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, non-root `netguard` user (Dockerfile); DEVICE_GATEWAY_ENABLED=True by default routes all device I/O through the Gateway, not this process; device credentials encrypted with a key (`DEVICE_CREDENTIAL_ENCRYPTION_KEY`) this process never receives (env_file split in compose) | None planned beyond what exists — this is the design's central assumption, not a gap | api can still forge NATS `jobs.request` messages if it holds `DEVICE_JOB_SIGNING_KEY` (it does, to sign legitimate jobs) — the Gateway's independent re-validation (tenant/device/approval/JIT/expiry, `app/device_gateway/validator.py`) is what stops a forged job from executing, not network isolation alone | `audit_logs` records every accepted *and* rejected Gateway job (Section 13) | Redeploy `api` from a known-good image; rotate `SECRET_KEY`/`DEVICE_JOB_SIGNING_KEY`; Gateway validator design means device state doesn't need "recovery" beyond normal incident response |
| T2 | Frontend XSS | Stored/reflected XSS in a device hostname, config diff, or user-supplied field rendered in React | React's default JSX escaping on all text nodes; no `dangerouslySetInnerHTML` audit performed this pass | Explicit audit of every `dangerouslySetInnerHTML`/`innerHTML` use in `frontend/src` (not yet done — open item) | Not verified this pass — flagged, not confirmed safe | No CSP header set in `app/main.py` currently — an XSS that lands has no defense-in-depth backstop | Standard incident response; session revocation via existing `RefreshToken` row revocation (`core/deps.py`) |
| T3 | Credential theft | RCE or DB dump exposes `Device.*_encrypted` columns | Two independent Fernet key hierarchies (`app/core/crypto.py`): general key (broadly distributed) vs. `DEVICE_CREDENTIAL_ENCRYPTION_KEY` (only `device-gateway`+`migrate` via `.env.device-gateway`); `credential_service.py` now correctly calls the device-scoped encrypt/decrypt functions for all 7 device columns (fixed this audit pass — was silently using the general key, defeating the split) | Key rotation exists (`secrets_rotation_service.py`, migration 0121) but hasn't been exercised against a real dataset — do that before production | A DB dump plus the general key alone still cannot decrypt device credentials; a DB dump plus `DEVICE_CREDENTIAL_ENCRYPTION_KEY` (only ever on `device-gateway`) can | `crypto.device_credential_active_key_count()` surfaced on the rotation status endpoint | Rotate `DEVICE_CREDENTIAL_ENCRYPTION_KEY`, run migration-equivalent re-encryption, force device credential re-entry if key itself is suspected compromised |
| T4 | JWT theft/forgery | `SECRET_KEY` (HS256, symmetric) exfiltrated from `api` process memory or env | Short `ACCESS_TOKEN_EXPIRE_MINUTES` (60) default; `sid` claim tied to a `RefreshToken` row checked for revocation on every request (real-time revocation, not just expiry); `validate_production_secrets()` refuses to boot on the placeholder `SECRET_KEY` | Migrate to Keycloak-issued, JWKS-verified (RS256) tokens for the OIDC path — local-auth HS256 path is a deliberate compatibility fallback (Section 1), not yet removable | HS256 means whoever signs can also verify — `SECRET_KEY` exposure is a full auth bypass for the local-auth path until sessions are individually revoked | Session list / revoke UI already exists | Rotate `SECRET_KEY` (invalidates all sessions immediately, including legitimate ones — no partial rotation for HS256) |
| T5 | Keycloak compromise | Keycloak container/DB compromised, or an admin credential leaked | Dedicated `keycloak-db` Postgres instance, separate from `netguard`'s DB (compose service `keycloak-db`); `api` container has no Keycloak admin API access (no admin credentials in its env block) | MFA/WebAuthin enforcement for Keycloak admins, admin console restricted to a management network (Section 16) — not independently verified this pass | Not verified this pass whether Keycloak's admin console is actually reachable only from a restricted network vs. the same `proxy` network as everything else | Keycloak's own security event logging (not independently confirmed enabled) | Revoke/rotate Keycloak realm keys; force re-login fleet-wide; NetGuard's own RBAC (Section 2) still gates every endpoint even if a Keycloak identity is compromised, limiting blast radius to what that specific mapped role can do |
| T6 | OpenBao compromise | OpenBao container compromised, unsealed and root-token exposed | `openbao` container: `read_only`, `cap_drop: [ALL]` + `IPC_LOCK`, `no-new-privileges`; only reachable from `netguard-secrets` (device-gateway) per network segmentation; manual init/unseal only (`openbao/bootstrap/bootstrap.sh`), not auto-unsealed by anything in compose; `device-gateway` uses a scoped AppRole (Role ID + rotatable Secret ID), never the root token | Real cloud-KMS auto-unseal or a documented manual unseal runbook for production (compose file explicitly leaves this out of scope) | The AppRole policy's actual least-privilege scope (`openbao/policies/device-gateway-policy.hcl`) wasn't re-diffed against the KV paths it needs this pass — verify it can't read/write outside `netguard-devices/` | OpenBao audit logging (Section 17) — presence not independently reconfirmed this pass | Revoke the AppRole's Secret ID, reseal/reinit if root token itself leaked (full credential re-entry required) |
| T7 | Database compromise | Postgres container/volume compromised or credentials leaked | `netguard_app` runtime role is `NOSUPERUSER`, owns no tables (no ALTER TABLE/trigger-disable rights by construction — verified: `docker/db-init/01-create-app-role.sh` + `alembic/grants.sql`); device credentials still encrypted at rest even inside a full DB dump (see T3) | None planned beyond what exists | A DB dump alone (without either Fernet key) still leaks metadata (hostnames, IPs, usernames, change history) even though it can't decrypt credentials | Postgres's own logging (not independently configured this pass — no `pgaudit` extension found) | Restore from backup, rotate both Fernet key hierarchies as a precaution, force full credential re-entry |
| T8 | NATS compromise | Unauthorized publish/subscribe on `jobs.request`/`jobs.result` | `nats-server.conf` (mounted at the correct path — a broken mount that silently disabled auth entirely was found and fixed in an earlier pass) requires per-service credentials; `device-gateway` connects via `NATS_URL` embedding `NATS_GATEWAY_USER`/`PASSWORD` | Subject-level ACL audit: confirm `api`'s NATS user truly cannot publish to `jobs.request` with an arbitrary payload bypassing `DEVICE_JOB_SIGNING_KEY` — not re-verified this pass | The Gateway's independent job-signature/tenant/device/approval revalidation (T1) is the real backstop here, not NATS ACLs alone — treat NATS auth as defense-in-depth, not the primary control | `audit_logs` entries for every job the Gateway processes, accepted or rejected | Rotate NATS credentials, restart `nats` with a fresh account config |
| T9 | Device Gateway compromise | RCE inside `device-gateway`, the one container with real device-network reachability and OpenBao AppRole access | `device-gateway`: `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, not on `proxy` (unreachable from the internet/Traefik directly); holds no Keycloak admin creds, no OpenBao root token, no JWT `SECRET_KEY` | This is the highest-value target in the whole architecture by design — it's the one process meant to hold device connectivity + device-credential decryption capability. No mitigation "closes" this; the design goal is containing blast radius to devices this specific AppRole/tenant scope can reach, not preventing compromise | A compromised Gateway can reach whatever the `netguard-execution` network is wired to in the real deployment (VLAN/subnet scope is environment-specific and explicitly left to the operator — compose only establishes the container-level isolation boundary) | Per-job audit trail is the primary detection surface; no device-side anomaly detection (e.g. unexpected config diffs outside a known change) implemented | Isolate the Gateway container/host, rotate `DEVICE_JOB_SIGNING_KEY` + `DEVICE_CREDENTIAL_ENCRYPTION_KEY` + the OpenBao AppRole Secret ID, audit every device the compromised AppRole could reach for unauthorized changes |
| T10 | Insider abuse | A legitimate, authenticated user (engineer/admin) intentionally misuses their access | RBAC + `extra_permissions` scoping (`core/permissions.py`); JIT elevation is device/operation/change-scoped with expiry enforced at execution time, not just grant time (`device_gateway/validator.py`); self-approval prevention (independent 403 check + Gateway-side re-verification) | Full Section 21 "insider" scenario walkthrough (e.g. a NETWORK_ADMIN quietly approving their own low-risk-classified change to avoid the four-eyes check) not specifically tested | Risk *classification* itself is currently rule-based, not independently reviewable before the fact — a determined insider who can influence how a change is classified could route around the approval gate | Full audit trail (WHO/WHAT/WHEN/DEVICE/CHANGE/APPROVAL/JIT for every mutating action) is the primary control, by design — this threat is fundamentally a detection-and-accountability problem, not a preventable-by-architecture one | Change-request/audit review process (organizational, not code) |
| T11 | Cross-tenant attack | A user in tenant A accesses/modifies tenant B's devices or data | `get_tenant_scope`/tenant_id filters used app-wide (spot-checked in `devices.py`, `change_requests.py` this and prior passes) | Exhaustive audit of every query across all 57 routers for a missing tenant filter — not done (would require per-endpoint review, out of scope for this pass) | Not fully verified — this remains the single largest unverified claim in the whole model | None specific beyond general audit logging | Tenant-scoped data export/comparison to detect if cross-tenant reads occurred, if ever suspected |
| T12 | Privilege escalation | A low-privilege user manipulates a request to gain a higher role's capabilities | `PERMISSION_MATRIX` (`api/rbac.py`) maps roles to resources server-side (not client-trusted); JIT elevation requires `require_roles` gate to even request; `implies_roles` on `extra_permissions` means a granted permission unlocks specific backend endpoints, not a blanket role swap | None planned beyond what exists | Vertical escalation via a missing `require_roles` on some newly-added endpoint is always possible if a route module forgets it — no automated "every mutating route has an auth dependency" check exists in CI (there is no CI — see T15) | 403s are logged; no automated alert on repeated 403s from one user | Audit the specific endpoint, add the missing dependency, review that user's session for what else they touched |
| T13 | Approval bypass / self-approval | A user approves their own change request, or a change executes without required approval | Explicit `requester != approver` 403 check plus independent re-verification inside the Gateway's own validator (two independent layers, confirmed by code read) — a narrow, audited exception exists for rollback changes specifically | None planned beyond what exists | The rollback self-approval exception is itself a residual risk surface if a rollback is ever used to smuggle through a non-rollback change — worth a dedicated test (not written this pass) | Audit log distinguishes rollback vs. normal approvals | Review the rollback exception's audit trail for misuse pattern |
| T14 | Replay of device commands | A captured/forged job message is replayed to re-execute a prior operation | Job signing (`DEVICE_JOB_SIGNING_KEY`, HMAC — `app/schemas/device_job.py`); Gateway validator checks expiry at execution time | Explicit nonce/idempotency-key check on job replay — not independently confirmed present (job TTL via `DEFAULT_JOB_TTL_SECONDS`/timeout_seconds limits the replay *window*, but doesn't by itself prevent a replay within that window) | A replay within the job's TTL window before it expires is not fully ruled out by what was verified this pass | `audit_logs` would show two identical operations close in time, if reviewed | Manual device state comparison against the change history if a replay is suspected |
| T15 | Supply-chain compromise | A malicious/vulnerable dependency or compromised base image | `requirements.txt` fully version-pinned (39/39 entries with `==`); backend Dockerfile pins `python:3.12-slim` by tag (not digest) | No CI pipeline exists in this repo at all — no dependency vulnerability scanning, no container image scanning, no SBOM generation, no secret scanning, no static analysis (Section 19 is entirely unimplemented) | This is the largest concrete, unimplemented gap found in this audit — everything in Section 19 needs to be added, not just hardened | None currently | Manual dependency review until CI exists |
| T16 | Host/container escape | A container breaks out to the host | No `privileged: true` or `network_mode: host` anywhere in `docker-compose.yaml` (grepped, confirmed); no `/var/run/docker.sock` mount anywhere; `read_only`+`cap_drop: [ALL]`+`no-new-privileges` on all 21 services except one documented exception (Grafana, which needs to write its own config at startup) | seccomp/AppArumor profiles beyond Docker's default not explicitly configured | `worker` has `cap_add: [NET_RAW, NET_ADMIN]` for nmap discovery (via setcap on specific binaries in the Dockerfile, not setuid/root) — the one deliberate exception to `cap_drop: ALL`, and a real (if narrow) escalation surface if `worker` itself is compromised | No host-level intrusion detection configured (out of scope for a compose file) | Standard container/host incident response |
| T17 | Denial of service | Resource exhaustion via request flooding, huge payloads, or slow clients | `deploy:` resource limits (mem/cpu) present on the Celery worker fleet and several other services (10 services, grepped) | No application-level rate limiting exists anywhere — `slowapi` is not in `requirements.txt`, and no rate-limiting middleware exists in `app/main.py`. No explicit request body size limit configured either. Both need adding | Any single authenticated (or, until Keycloak/OIDC is the only path, unauthenticated login-endpoint) client can currently send unlimited requests | None | Traefik-level rate limiting could be added as a stopgap; not currently configured |
| T18 | Audit tampering | An attacker with DB access tries to modify or delete historical audit records | Two independent layers verified this and a prior pass: `netguard_app` is `NOSUPERUSER`, owns no tables (no ALTER TABLE/trigger-disable rights); `UPDATE`/`DELETE` explicitly revoked on `audit_logs` specifically (`alembic/grants.sql`); a `BEFORE UPDATE/DELETE` trigger on top of that | None planned beyond what exists — both layers were independently confirmed sufficient to stop the RCE-in-`api` threat model | The owning DB role (used only by `migrate`) *can* still alter `audit_logs` — that's an inherent limit of any DB-level append-only control, not a bug; it's why `migrate` itself needs to be tightly access-controlled operationally | Any unexpected `migrate`-role activity outside a deployment window is the signal to watch for | Restore `audit_logs` from a WAL-based point-in-time backup if tampering via the owning role is ever suspected |

## Notes on what this table does and doesn't claim

- Rows marked "not independently verified this pass" (T2, T5's Keycloak network
  restriction, T6's AppRole policy scope, T8's NATS ACL granularity, T11's
  full tenant-filter coverage) are **not confirmed either way** — they're
  flagged as open verification work, not asserted as safe or unsafe.
- T15 (supply chain) and T17 (DoS/rate limiting) are the two rows with a
  **concrete, confirmed-absent** control, not just an unverified claim — these
  are the two clearest "add this" items from this pass.
- Per Section 22, this table does not claim the system is "100% secure" and
  none of the rows above should be read that way.
